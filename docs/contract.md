# Контракт backend ↔ frontend

Меняет сессия бэкенда. Живой пример: `docs/sample-snapshot.json` (ответ на демо-файле 5 000 инцидентов).
**Изменения 20.11** (разбор, `docs/decisions.md`): лёгкий снимок + серверный поиск, «Взять в работу» в файле
вместо «Принял»/claims, конфликт правок (409), история изменений, порядок колонок. Отмечены ⚑.

## ⚑ Что фронту поменять (20.11) — коротко
1. **«Принял» удалён.** `POST /api/alerts/ack` больше нет (сейчас отвечает `405 Method Not Allowed`), заглушки не будет.
   Кнопки «✓» / «Принять все» в строке тревог убрать. Тревогу у всех снимает **«Взять в работу»**:
   `POST /api/incidents/{id}/claim {by, expected_hash?, force?}`; «Отпустить» — `DELETE /api/incidents/{id}/claim?by=<имя>`.
   Подробно — раздел «Тревоги и „Взять в работу“».
2. **Тревога не взята**, пока `alert.taken_by == null`. Кто взял — `alert.taken_by` и `incident.coordinator = {name, at}`
   («в работе у Ольги»). Отпустили, а инцидент всё ещё в группе, — тревога снова не взята.
   Взят кем-то и стал критическим: громко только у того, чьё имя в `taken_by`, остальным тихая строка.
3. **В `snap.incidents` только видимые** (из групп + взятые в работу + из очереди), не все. Счётчик «ещё N вне групп» —
   `snap.outside_active`. Поиск и фильтры по всем инцидентам — `GET /api/search` (раздел «Поиск и фильтры»): номер,
   продукт, команда, «в работе у X»/мои, просроченные, горит срок, непринятые тревоги, без исполнителя, риск ИИ, дубли,
   клиентские/внутренние, новые за час. Инцидент не из снимка — `GET /api/incidents/{id}`.
4. **Конфликт правок:** во все правки передавать `expected_hash: incident.hash`; изменился → `409 {conflict, changes}`
   → «Инцидент только что изменили: … Обновить?». После своего действия брать новый `hash` из ответа.
5. Новые типы событий `taken`, `released`; «на координаторах» уже отсортированы сервером (дольше ждёт — выше).

## Как фронту получать данные
Опрос `GET /api/snapshot` раз в 1 с с заголовком `If-None-Match: <ETag из прошлого ответа>`.
Ничего не поменялось → `304` без тела. Поменялось → `200` с полным снимком и новым `ETag`.
⚑ Ответ сжат gzip (браузер распаковывает сам), сериализуется один раз на версию для всех экранов.
Правка файла видна на сервере за ≤0,5 с (опрос mtime+size раз в 0,25 с; частые правки склеиваются, не чаще раза в 0,5 с),
пересчёт на 5 000 инцидентов ~0,15–0,6 с → на экране ≤1–1,5 с. Действия из АРМ/ITSM применяются сразу (без опроса).

Если открытая панель ссылается на инцидент, которого нет в снимке, — взять его через `GET /api/incidents/{id}`.

### Порядок в колонках ⚑ (decisions.md, п. 3)
- critical, high: просроченные → по оставшемуся времени → без срока; решённые («висят 30 мин») внизу;
- coordinators: **дольше ждёт у координаторов — выше** (по `assigned_to_team_at`, иначе `created_at`);
- research: новые сверху (по `resolved_at`, иначе `created_at`).

## ИИ (поле `ai` у Incident, `ai_status` в снимке)
Владелец — сессия ИИ (`backend/app/ai/`). Правила считают всё мгновенно; GigaChat в фоне дописывает слова, снимок его
никогда не ждёт. Числа (уверенность, баллы риска) — всегда из правил и истории, не со слов модели.
**Метка «ИИ» и кнопка «почему?»** — у каждой функции есть `source` (`rules` | `gigachat` | `cache` — ответ GigaChat из
кэша прошлого запуска) и `at` (реальное время ответа, ISO UTC).

Инциденты **на экране** (в группах, кроме «решён», или отмеченные динамикой) получают полный объект.
Остальные — компактный: только непустые поля, без `summary_meta`, `breakdown` и подробностей дублей.
Отсутствующее поле = `null`.

```jsonc
"ai": {
  "source": "rules",                 // rules | gigachat | cache — есть ли в карточке слова GigaChat
  "pending": false,                  // GigaChat ещё думает над этим инцидентом (можно показать «…»)

  // 8.1 Выжимка — показывать вместо длинной сути (оригинал — в панели)
  "summary": "Абоненты не могут войти в Зеркальце: SMS-код не приходит",   // ≤ 90 знаков

  // 8.2 Кому передать — только у «на координаторах» (активные/исследование), иначе null
  "route": {
    "team": "КЦ Ступа",
    "confidence": 0.8,                       // доля похожих, которые вела эта команда (по истории!)
    "confidence_text": "8 из 10 похожих",    // так и писать на карточке: «ИИ: передать в «КЦ Ступа», 8 из 10 похожих»

  // 8.5 Тревожная динамика — у любых активных (включая средние/низкие), иначе null

    "kind": "text",                         // text — похожий текст (видно и без GigaChat);
```

`ai_status` в снимке (и в `/api/health` → `ai`):
```jsonc
{"provider": "gigachat",            // rules — GigaChat выключен (LLM_PROVIDER=rules)
 "state": "ok",                     // ok | starting | limited (429: ответы задерживаются, повтор через 5–60 с)
                                    // | offline (нет связи — работают правила, повтор раз в минуту) | off
 "label": "ИИ: нет связи с GigaChat, работают правила",   // готовая подпись для шапки/плашки
 "error": null, "queue": 12, "in_flight": 2, "done": 140, "cached": 480,
 "last_ok_at": "...", "next_retry_at": "..."}
```

Связка с бэкендом:
- «Да, это один сбой» → `POST /api/duplicates/confirm` `{"master_id": "...", "ids": [...], "by": "Ольга"}`
  (`master_id` и `ids` — из `ai.duplicates`): в файл `isMaster` у мастера, `isDouble` у остальных + `workLog`;
  ответ `{ok, incidents: [...]}`, после этого у группы `duplicates.confirmed = true`.
- История изменений: основная — бэкенда (`refs.history`, передаётся в `ai.enrich(..., refs=refs)`), по ней ИИ ищет
  тревожную динамику. Без `refs` ИИ копит запасную сам (`ai.history(id)`, `cache/ai_history.json`).

## Поиск и фильтры по всем инцидентам ⚑ — `GET /api/search`
Параметры (все необязательные; списки — через запятую):

| Параметр | Что |
|---|---|
| `q` | по номеру, продукту, команде, сотруднику, координатору, тексту (заголовок, описания, сервис, сценарий); слова — все должны встретиться; без учёта регистра |
| `status` | `all` (по умолчанию) · `active` · `done` (решённые/закрытые/исследование) |
| `product`, `team` | точное совпадение, можно несколько |
| `priority` | id через запятую: `4,3` |
| `coordinator` | «в работе у X» (без учёта регистра); «мои» = своё имя |
| `group` | `critical` / `coordinators` / `high` / `research` |
| `overdue` | только просроченные (`forecast.level = overdue`) |
| `burning` | горит срок: прогноз «не успеют» или просрочен |
| `untaken` | непринятые тревоги: в «критических»/«на координаторах» и никто не взял |
| `unassigned` | активные без сотрудника-исполнителя |
| `risk_high` | высокий риск ИИ (`ai.risk.level = high`) |
| `duplicates` | дубли и массовые (`is_master` / `is_double` / `ai.duplicates`) |
| `service_type` | `client` (Клиентский) · `internal` (остальные) |
| `new_hour` | созданы за последний час |
| `limit`, `offset` | страница (по умолчанию 100, максимум 500) |

Ответ: `{"total": 340, "items": [Incident, ...], "offset": 0, "limit": 100, "now": "..."}` → «12 из 340».
Порядок: точное совпадение номера первым, активные выше решённых, выше приоритет, меньше осталось времени, новее.
На 5 000 инцидентов — ~20 мс.

## Тревоги и «Взять в работу» ⚑ (decisions.md, п. 4, 7)
Кнопки «Принял» нет, `POST /api/alerts/ack` **удалён**. Тревогу снимает «Взять в работу» — оно пишется в файл
полем `coordinator` (и в `work_log`), поэтому видно на стене и всех АРМ и переживает перезапуск.
```jsonc
Alert = {"key": "critical:INC…", "group": "critical" | "coordinators", "incident_id": "INC…",
         "since": "…",                 // начало эпизода (вошёл в группу); повторный вход — новый эпизод
         "taken_by": "Ольга" | null, "taken_at": "…" | null,   // из поля coordinator инцидента
         "acked_by": …, "acked_at": …} // = taken_by/taken_at, оставлено для старого фронта
```
Тревога «не взята», пока `taken_by == null`. Отпустили, а инцидент всё ещё в группе — снова не взята.
«Уже в работе у кого-то и стал критическим → громкая тревога только у владельца» — фронт сравнивает `taken_by` со своим именем.

Порядок: критические первыми, внутри — по оставшемуся времени.

## Event
```jsonc
{
  "seq": 4, "type": "became_critical",
  "incident_id": "INC...", "title": "...", "product": "...",
  "before": "Высокий", "after": "Наивысший",
  "alert": "critical",                // critical | coordinators | critical_resolved | null
  "text": "стал критическим: Высокий → Наивысший",
  "by": "Ольга",                      // автор, если правка из АРМ/ITSM или с записью в workLog
  "at": "...реальное время...", "clock_at": "...время дашборда..."
}
```
Типы: `new, removed, became_critical, critical_resolved, to_coordinators, from_coordinators,
priority_changed, deadline_changed, team_changed, assignee_changed, status_changed, resolved, reopened,
comment, escalated,` ⚑ `taken, released`. При старте сервера и при подмене файла целиком событий нет (базовая точка).

## Остальное
- `GET /api/incidents/{id}` — Incident + `raw` (исходная запись из файла) + ⚑ `history` (история изменений, см. ниже)
  для панели деталей. Работает для любого инцидента, не только из снимка.
- `GET /api/events?after=<seq>` — события после seq.
- `GET /api/health` — статус файла, версия, ⚑ `last_apply_seconds` (сколько занял последний пересчёт).

### История изменений ⚑ (`history` в `/api/incidents/{id}`; для ИИ — `backend/app/history.py`)
```jsonc
[{"at": "…", "kind": "priority" | "team" | "assignee" | "deadline" | "state" | "reopen",
  "before": "Средний", "after": "Высокий", "by": "Ольга" | null,
  "up": true,                          // priority
  "before_id": 2, "after_id": 3,       // priority, state
  "later": true, "shift_min": 120}]    // deadline
```
Старые → новые. Сервер копит сам (и правки жюри, и действия АРМ), хранит в `cache/history.jsonl`,
при первом появлении инцидента засевает из `work_log` с полями `kind/before/after`.

## Действия (пишут в файл инцидентов; ответ — обновлённый Incident)
Во **всех** правках можно передать ⚑ `expected_hash` — `hash` инцидента, который видел координатор.
Если запись в файле с тех пор изменилась, правка **не сохраняется**, ответ `409`:
```jsonc
{"detail": "инцидент только что изменили — обновите карточку, правка не сохранена", "conflict": true,
 "hash": "<текущий>", "changes": [{"field": "priority", "label": "приоритет", "before": "Высокий",
                                   "after": "Наивысший", "text": "приоритет: Высокий → Наивысший"}, …]}
```
→ «Инцидент только что изменили: … Обновить?». После своего действия брать новый `hash` из ответа.

| Метод | Тело | Что делает |
|---|---|---|
| ⚑ `POST /api/incidents/{id}/claim` | `{by, expected_hash?, force?}` | «Взять в работу»: `coordinator` в файл + журнал; тревога снята у всех. Уже у другого → `409 {"detail", "coordinator"}`; `force: true` — забрать себе. Решённый → 400 |
| ⚑ `DELETE /api/incidents/{id}/claim?by=Имя&expected_hash=…` | — | «Отпустить»: снять `coordinator` + журнал |
| `POST /api/itsm/{id}/assign` | `{team, assignee?, comment?, by, expected_hash?}` | передать в команду (Выполняется → Назначен); ⚑ снимает `coordinator` |
| `POST /api/itsm/{id}/state` | `{state_id, reason?, comment?, by, expected_hash?}` | смена статуса по `transitions` из АРМ или мини-ITSM, АРМ передаёт `expected_hash` |
| `POST /api/itsm/{id}/priority` | `{priority_id, recalc_deadline?, comment?, by, expected_hash?}` | приоритет (+ срок по SLA) |
| `POST /api/itsm/{id}/deadline` | `{deadline (ISO UTC), comment?, by, expected_hash?}` | срок |
| ⚑ `POST /api/duplicates/confirm` | `{master_id, ids, by}` | «Да, это один сбой»: `isMaster` у мастера, `isDouble` у остальных + журнал (`action: duplicates`), одной записью. Ответ `{ok, incidents: [Incident…]}` |
| `POST /api/itsm/{id}/comment` | `{text, by}` | комментарий в журнал |
| `POST /api/itsm/{id}/escalate` | `{comment?, by}` | эскалация (в журнал) |
| `GET /api/meta` | — | статусы, переходы, приоритеты, SLA, команды |
| `GET /api/export` / `POST /api/import` | — / JSON-файл | скачать / заменить файл (старый → `cache/backups`) |

Ошибки: 400 (нельзя по правилам), 404, 409 (конфликт, уже в работе у другого, файл сейчас битый/занят — правка не сохранена).
⚑ Перед каждой записью — копия файла в `cache/backups` (храним 20, `BACKUPS_KEEP`).

## Справочники для ИИ ⚑ (договорённость бэк ↔ ИИ)
Store на каждую правку строит `backend/app/refs.Refs` одним проходом и вызывает
`ai.enrich(incidents, now, rules, refs=refs)`, если у `enrich` есть параметр `refs` (иначе — старую сигнатуру).
ИИ берёт из refs только `refs.history.get(id)` (O(1), записи только читать). Когда GigaChat дописал ответы
(`ai.consume_dirty()`), Store вызывает только `ai.enrich` и пересобирает очередь действий — прогноз не пересчитывается.
`refs.changed` / `refs.removed` — id изменённых по `hash`; `refs.median_resolution(team, prio)`; `refs.history` — история
выше (формат совместим с `ai/dynamics.History.get()`). Справочник «кому передать / всплеск» — у ИИ (`ai/index.py`).
Замер: `python scripts/bench.py` (5 000 и 10 000), автотест `backend/tests/test_speed.py`.

## Сбои v2: первый сценарий между продуктами

ИИ предоставляет `ai.outage_candidates()` после `ai.enrich()`. Элемент списка: `{master_id, ids, name, reason, source}`.
`ids` включает `master_id`. Правила ищут всплеск по общему `productMasterId`: минимум три активных инцидента,
минимум два продукта, не более 15 минут от первого до последнего. GigaChat в фоне может уточнить состав,
название и объяснение. `source` принимает `rules`, `gigachat` или `cache`. Пока модели нет, объяснение показывает
наблюдаемые совпадения. Общий код и время позволяют предложить связь для проверки координатором.

В `/api/snapshot` появляются два поля:

```jsonc
"outage_candidates": [{"id": "…", "name": "…", "reason": "…", "source": "rules", "incident_ids": ["INC…"],
                       "products": ["…"], "active_count": 3, "priority_id": 3, "deadline": "…"}],
"outages": [{"id": "…", "name": "…", "reason": "…", "source": "rules", "incident_ids": ["INC…"],
             "products": ["…"], "active_count": 3, "priority_id": 3, "deadline": "…", "status": "active"}]
```

У подтверждённого сбоя `status` принимает `active` или `resolved`. Приоритет и ближайший срок считаются по
активным участникам, при отсутствии данных поле равно `null`. Решённый сбой остаётся в снимке до 30 минут
после решения последнего участника. Отсутствие записи в `snapshot.incidents` не исключает её из `incident_ids`.
Группы инцидентов и их счётчики сохраняют прежние правила.

- `POST /api/outages/confirm` с `{candidate_id, by}` подтверждает показанный состав. Возвращает объект из `outages`.
  Сервер сверяет текущую версию кандидата и записи участников перед единой транзакцией в JSON. Устаревший
  кандидат или изменённая запись дают `409`. Фронт обновляет снимок перед повтором.
- `GET /api/outages/{id}` возвращает объект сбоя плюс `incidents` (список объектов Incident с полями карточки).
- `GET /api/outage-candidates/{id}` возвращает предложение и `incidents` с `id`, `title`, `product`
  и `cause_incident_id` при наличии. Состав доступен в одном запросе, включая заявки вне снимка.
- `DELETE /api/outage-candidates/{id}/incidents/{inc_id}` с `{by}` исключает заявку до подтверждения.
  Сервер проверяет версию всего показанного предложения. При изменении возвращает `409` без записи.
  Успех возвращает `{candidate: обновлённое предложение или null}` и сохраняет исключение в журнале.
  Оставшийся подходящий состав нужно подтвердить отдельно. Допускаются две связанные заявки после ручного исключения.
- `DELETE /api/outages/{id}/incidents/{inc_id}` исключает участника из подтверждённого сбоя. Тело запроса:
  `{by, expected_hash, expected_incident_ids}`. При изменении записи или состава возвращается `409` без записи.
  Успех возвращает `{outage: объект с incidents}`. Если оставшихся участников меньше двух, сбой распускается
  и возвращается `{outage: null}`. Статусы, владельцы и исполнители сохраняются. Действия отражаются в `workLog`.
  Связка исключённой заявки с прежними участниками сохраняется в файле (`outageExclusions`). Эту связку
  не предлагают повторно. Допустимы новые сбои с другими заявками.
- `POST /api/outages/{id}/actions` применяет `claim`, `assign` или `escalate` ко всем активным
  участникам. Запрос принимает `by`, `operation`, `expected_hashes` (`id → hash` активных участников),
  для `assign` обязательно `team`, для `assign` и `escalate` возможен `comment`. Изменение хотя бы одной
  заявки, состава или чужой координатор дают `409` без записи. Успех возвращает обновлённый сбой с `incidents`.
  Действие записывается в `workLog` каждой затронутой заявки с ID сбоя. Решённые и закрытые заявки сохраняются как есть.
  Детали доступны и после исчезновения из снимка. До подтверждения участники доступны через `/api/incidents/{id}`.
- В JSON у каждого участника сохраняется `outage: {id, master_id, name, reason, source}` и запись в `workLog`.
  Идентификатор и состав восстанавливаются из файла после перезапуска. Межпродуктовая корреляция хранится в
  отдельном поле. Флаги дублей и прежний маршрут `/api/duplicates/confirm` продолжают обозначать дубли.

На стене показываем подтверждённые сбои. В АРМ раздел «Сбои» содержит предложения, подтверждение и состав.
В первом сценарии доступны обычные действия над отдельными инцидентами.

## Повторные сбои

У активного `Incident` в снимке, поиске и деталях может быть объект `recurrence`:

```jsonc
"recurrence": {"count": 2, "level": "strong", "suggested_team": "КЦ Избушка",
               "cases": [{"id": "INC…", "title": "…", "resolved_at": "…", "team": "…",
                          "solution": "…", "state_reason": "Постоянное решение"}]}
```

Узел определяется парой `service` и `scenario`. История включает решённые записи с `completionDate` за семь суток
до регистрации текущего инцидента. Решение должно предшествовать регистрации. `count` — число таких записей,
`cases` — до пяти последних, новые первыми. `strong` означает, что среди этих записей есть «Постоянное решение»,
иначе уровень `soft`. `suggested_team` — подходящая команда из прошлого случая, либо `null`. Назначение остаётся
действием координатора. Если совпадений нет, `recurrence` отсутствует или равно `null`.

## Модели GigaChat

`GIGACHAT_MODEL` задаёт базовую модель для выжимки и пояснения динамики. Если задана
`GIGACHAT_MODEL_ADVANCED`, маршрутизация, пояснение риска и проверка групп выполняются на ней.
Обе модели используют общую фоновую очередь и лимит запросов. Кэш учитывает модель.
При ответе `402`, `403` или `404` фоновые запросы продолжаются на базовой модели до перезапуска.

## Персональная очередь и метки

- `GET /api/queue?by=Ольга` → `{items: [QueueItem, …]}`. Без имени выдаются только свободные задачи.
  С именем видны свободные задачи и задачи этого координатора. Действие другого координатора не показывается.
- `QueueItem` расширяет `Action`. Поля `incident_id` и `outage_id` допускают `null`. `incident` — компактное
  описание инцидента (`id`, `title`, `product`, `deadline`, `priority_level`, `itsm_url`) либо `null`.
  Виды: `claim`, `route`, `escalate`, `outage`, `dynamics`, `aftermath`, `deadline`, `recurrence`.
- `POST /api/queue/preferences` с `{by, id, operation}`. `operation`: `snooze` на 15 минут или `dismiss`.
  Успех → `{ok: true}`. Предпочтение хранится для этого координатора. Действия над инцидентом идут через текущие API.
  Для `outage` значение `outage_id` — ID предложения для `/api/outages/confirm`, отклонение скрывает предложение в личной очереди.
- У `Incident` может быть `labels: ["waiting_external", "aftermath", "clients_affected", "reassigned", "recurrence"]`.
  Ожидание и последствия берутся из полей выгрузки. Перекидывание определяется по истории смены команды.
  На карточке показывается до двух меток, включая повтор. В панели доступен полный набор.

## Исправления подсказок ИИ

- `POST /api/incidents/{id}/ai-feedback` принимает `by`, `expected_hash`, `kind` (`route`, `summary`,
  `risk`, `dynamics`). Для `route` также обязательны предложенная `expected_team` и выбранная `corrected_team`.
  Изменение заявки или предложенной команды даёт `409`, успех — `{ok: true, saved: true}`. Повтор возвращает `saved: false`.
- `cache/ai_feedback.json` хранит последние исправления на координатора, заявку и тип подсказки. Имя координатора
  и исходные тексты подсказок хранятся в виде хешей. Выбор команды влияет на следующие заявки по совпадению
  продукта, сервиса и сценария. История передач и исправления считаются раздельно. В запрос GigaChat включаются
  счётчики и до трёх пар названий команд. Отметки о выжимке, риске и динамике хранятся для разбора.

## Причина и следствия

Поле `causeIncidentId` в файле необязательно. Если оно содержит строковый ID заявки-причины, в `Incident`
появляется `cause_incident_id`. Сервер собирает цепочки действующих заявок вокруг корневой причины, включая
связи между продуктами. Неизвестные и неактивные причины, замкнутые цепочки и участники подтверждённых
сбоев исключаются. Для явной связи достаточно двух заявок. Булевы флаги выгрузки сами по себе цепочку не создают.
Предложение появляется в «Сбоях» и «Очереди». Подтверждение использует тот же API и журнал работ, что и другие сбои.
